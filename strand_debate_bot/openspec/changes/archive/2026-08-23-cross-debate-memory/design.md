## Context

See `proposal.md` - Why for motivation. This builds directly on the archived `core-debate-graph` change: the `moderator` hub reading/advancing `invocation_state["round"]`, `AgentTurnNode` building a prompt from `invocation_state` and calling its own `Agent` once, and `ModeratorDecision` as the single terminal node producing the structured verdict. `src/core/prompts.py` currently has no memory concept at all (its own docstring flags this as deliberately deferred to this change). The old LangGraph system's `src/core/memory.py` and its per-turn `build_memory_block(state["memory_context"])` calls in `pro.py`/`con.py` were read directly and are the working reference for retrieval shape, the 1200-character cap, and the "do not reference explicitly" framing.

## Goals / Non-Goals

**Goals:**
- A Chroma-backed store implementing `strands.memory.types.MemoryStore` (`search` + `add`), embedding with Chroma's bundled default function.
- Exactly one retrieval call per debate run, inside `ModeratorHub`'s one-time `"" → "opening"` round transition, best-effort (a store failure degrades to no context rather than blocking the debate).
- `invocation_state["memory_context"]` threaded into every Pro/Con opening, rebuttal, and closing prompt builder for the rest of the run.
- Exactly one write call per debate run, inside `ModeratorDecision`, immediately after the verdict is computed.
- The 1200-character combined cap and the "do not reference explicitly" instruction, preserved from the old system.

**Non-Goals:**
- The audience-question turns (`pro_addresses_question`/`con_addresses_question`) don't exist yet — they're Task 4's `audience_question` node body. This change does not add them; Task 4 is responsible for giving those prompt builders the same `memory_context` splice once they exist.
- Any use of `strands.memory.MemoryManager`'s search/add tools or injection middleware — deliberately not used (see Decisions).
- Swapping the store's backend for a managed/AWS vector store — that's the later AWS-target stage (PRD Open Question 6), not this change.
- Any change to round order, edge structure, or verdict content/shape — this change only adds retrieval/write side effects to two already-existing nodes and injects content into already-existing prompt builders.

## Decisions

**Call the `MemoryStore`'s `search`/`add` directly from node code; do not use `MemoryManager`.** `MemoryManager`'s tool/injection machinery is built for one `Agent` deciding for itself, mid-conversation, when to recall or store a fact about "the user," deriving its query from that agent's own latest message. This debate's retrieval is deterministic (always once, before any turn, driven by `invocation_state["topic"]`) and spans multiple separate `Agent` instances with no shared conversation — there is no single agent conversation for injection middleware to attach to. A model-visible `search_memory` tool would also let the model know it's recalling something, contradicting the requirement that retrieved context not be referenced explicitly. Alternative considered: wrap the store in a `MemoryManager` configured with every feature disabled (`search_tool_config=False, add_tool_config=False, injection=False`) purely as an async façade — rejected as needless indirection: with exactly one store and none of the manager's own behavior in use, the only thing it would add is an async wrapper and tracing spans, not worth carrying the dependency whose entire purpose is switched off.

**Retrieval is unfiltered top-k, not thresholded by an absolute similarity score.** `search` returns whichever entries are nearest in the collection, up to `max_search_results`, even if the nearest one is a poor match — there is no minimum-similarity cutoff below which it returns nothing instead. This matches the old system's `similarity_search(query, k=2)`, which has no threshold either, and avoids inventing an arbitrary cutoff value that was never discussed or tuned. The practical effect: once the store holds at least one entry, every subsequent debate's opening/rebuttal/closing turns carry *some* past-debate context, however tenuously related; only a genuinely empty store yields none. Alternative considered: add a distance threshold so a dissimilar topic gets no context — rejected for this change as an undiscussed, untested addition; worth revisiting later if a real debate shows an unrelated summary being injected.

**Chroma's bundled default embedding function, not the old `langchain_huggingface` + `sentence-transformers` stack.** Same embedding quality class (MiniLM), far smaller footprint — this project's `requirements.txt` is currently 5 lines with no torch/langchain at all. Alternative considered: port the old embedding dependency unchanged for closest fidelity — rejected, since no requirement calls for that specific model, only "semantically similar," and the dependency weight buys nothing at the requirement level.

**Single retrieval site: `ModeratorHub`, on its `"" → "opening"` transition, guarded by the round check and wrapped in try/except degrading to an empty context.** `ROUND_TRANSITIONS` never revisits `"opening"` within a run, so this fires exactly once with no dedup logic needed. The hub already produces a content-less node-completion event on every visit (which the SSE/UI layer must already special-case), so adding invisible I/O here introduces no new category of "silent node" for that layer to handle. Wrapping it in try/except keeps a store failure from cascading into "no debate can start," since the hub is the one mandatory routing point every run passes through. Alternative considered: a dedicated `memory_retrieval` node inserted before `pro_opening` — rejected: identical content outcome, but adds a graph node, two edges, and one more silent SSE event needing UI filtering, in exchange for an isolated-unit-test benefit that testing the hub's `invoke_async` output already gives (assert on `invocation_state["memory_context"]` after the call, same as a separate node's test would).

**Single write site: `ModeratorDecision`, immediately after `winner`/`justification` are set.** Mirrors the precedent already set by keeping `moderator_decision` a separate, independently-testable terminal node (`core-debate-graph`'s Design Decision 3): the graph itself unambiguously knows when a debate is done and what its verdict is, so the write belongs where that fact is established. This also avoids the old system's multi-call-site write (`upsert_debate` called from the service layer at 4+ endpoints) — a duplication this change deliberately does not reintroduce. Alternative considered: write from the API/service layer after the graph completes, matching the old system exactly — rejected for reintroducing that same "forgot one call site" bug class.

**`memory_context` threaded via `invocation_state`, spliced explicitly by every relevant prompt builder.** Forced by `pro.py`/`con.py`: each turn's `Agent` is freshly constructed and called once, with no shared conversation across turns, confirmed by reading the current node factories directly. There is no automatic-propagation alternative available here — relying on `MemoryManager`'s agent-attached injection was already rejected in the first decision, and would not work across the several separate `Agent` instances a debate uses regardless.

## Risks / Trade-offs

- [Risk] Every opening/rebuttal/closing prompt builder must remember to splice `memory_context` in; a prompt builder added later (Task 4's audience-answer turns) that omits it silently breaks the "every turn" parity this change establishes → [Mitigation] tests assert the memory block's presence in each turn's rendered prompt text, extending the existing rendered-prompt-assertion idiom from `tests/test_graph.py`; this document and the PRD's FR-4 flag the audience-answer turns as needing the same treatment when Task 4 adds them.
- [Risk] Swallowing retrieval failures in try/except could mask a persistent misconfiguration (e.g. a bad persist directory) as "no memory available," indefinitely and invisibly → [Mitigation] log the exception where it's caught, so it stays diagnosable via existing logging without surfacing in the debate's own output.
- [Risk] Chroma's default embedding function fetches a small ONNX model on first use; a fully offline first run would fail that fetch → [Mitigation] this is a local one-time-setup cost, not a debate-blocking one — a failed model download is just another retrieval failure, and still degrades to no context per the requirement above.

## Migration Plan

Greenfield addition — no existing consumer of a memory concept exists in this codebase yet (the old LangGraph system's equivalent lives in a different, unrelated repo). No rollback plan beyond removing the new store module, its call sites in `ModeratorHub`/`ModeratorDecision`/the prompt builders, and the `chromadb` dependency.
