## Context

See proposal.md - Why/What Changes for motivation. Relevant constraints this design builds on, confirmed directly against the installed `strands` package (1.53.0):

- `Graph.__init__` constructs `self.state = GraphState()` (empty) and then synchronously fires `MultiAgentInitializedEvent` before returning. A wired `SessionManager` reacts to that event via `initialize_multi_agent`: if nothing is on disk yet, it writes an initial checkpoint immediately (`create_multi_agent`) — before any node has executed, without any explicit call from application code.
- `Graph.serialize_state()` is called automatically on `AfterNodeCallEvent` and `AfterMultiAgentInvocationEvent` (via `SessionManager.sync_multi_agent` → `FileSessionManager.update_multi_agent`). Its payload is topology only: `completed_nodes`, `failed_nodes`, `interrupted_nodes`, `node_results` (each node's bare `MultiAgentResult.to_dict()`), `next_nodes_to_execute`, `current_task`, and `_internal_state.interrupt_state`. It does **not** include `invocation_state`.
- Every node in this codebase (`AgentTurnNode` in `src/core/nodes.py`; `ModeratorHub`, `AudienceQuestionStub`/`AudienceQuestionHook`, `ModeratorDecision` in `src/agents/moderator.py`) writes its output only into `invocation_state[key] = ...` and returns a bare `MultiAgentResult(status=Status.COMPLETED)`. So `node_results` — the one piece of per-node output Strands does persist — never carries any debate text either. `invocation_state` is a plain dict that exists only in whichever Python frame is holding it; `Graph` never owns a reference to it beyond a single `invoke_async`/`stream_async` call (`self._current_invocation_state`, not part of `serialize_state()`'s payload).
- `Graph.deserialize_state()` restores `next_nodes_to_execute` and sets `self._resume_from_session = True` when there's mid-execution state to resume into; `stream_async`/`invoke_async` check that flag to decide whether to reset `GraphState` or continue from the persisted one. `_interrupt_state` round-trips through the same payload, so a run killed mid-interrupt has its pause state restored by Strands itself, with no extra code.
- `debate-fastapi-surface` (prerequisite, in-progress) defines `RunRegistry`/`RunEntry` as explicitly non-durable, in-process-only state whose job is bridging one HTTP request/response boundary within a single process lifetime (design.md, Decision 1 of that change). It does not exist yet in code beyond schemas/exceptions/the registry class itself.

## Goals / Non-Goals

**Goals:**
- Make both halves of a run's state — topology (which nodes ran) and content (`invocation_state`) — durable across a process restart, using `FileSessionManager` for the former and an application-level mechanism for the latter, since Strands does not provide the latter.
- Guarantee that any `run_id` a client has been given is resumable, regardless of how early the process dies after issuing it.
- Keep every node's contract exactly as-is: `invocation_state` in, `invocation_state` out. Durability is bolted on around the nodes, not threaded through them.

**Non-Goals:**
- Any cloud/S3/AgentCore session backend — that is the PRD's later AWS-stage swap, not this change.
- Any multi-node coordination, ownership, or heartbeat mechanism — already excluded project-wide.
- Changing how the audience-question interrupt itself works — `audience-question-hitl`'s hook is untouched; this change only ensures the graph object that hook attaches to can be reconstructed after a restart.

## Decisions

### 1. `invocation_state` gets its own persistence, via a `HookProvider`, not by changing node return contracts
A dedicated `HookProvider` (registered on the graph alongside `AudienceQuestionHook`) listens for `AfterNodeCallEvent` and `AfterMultiAgentInvocationEvent` — the exact same events `SessionManager` itself listens to for `sync_multi_agent` — and on each one, writes the current `invocation_state` dict as JSON to `invocation_state.json` inside that run's `FileSessionManager` session directory (`storage_dir/session_<run_id>/invocation_state.json`). On resume, before calling `invoke_async` again, the caller reads that file back into a plain dict and passes it as the `invocation_state` argument.

Alternative considered: change every node to return its output via `MultiAgentResult`'s result payload instead of (or in addition to) mutating `invocation_state`, so Strands' own `node_results` — which is already persisted — carries the content, then reconstruct `invocation_state` from `node_results` after `deserialize_state()` runs. Rejected: this fights the codebase's one established node contract (`nodes.py`'s own docstring: "every node's data flow uniform: invocation_state in, invocation_state out" — design.md Decision 4 of `core-debate-graph`), would require every node to grow a second output path, and still needs a hand-written reconstruction step on resume (`node_results` keyed by node id, not by the field names `invocation_state` uses) — no less custom code, for a bigger blast radius.

Alternative considered: subclass or wrap `FileSessionManager` itself to also persist `invocation_state` as part of its own multi-agent payload. Rejected: `serialize_state()`/`deserialize_state()` are methods on `Graph` (the `MultiAgentBase`), not on the session manager — reaching `invocation_state` into that payload would mean overriding `Graph.serialize_state()` itself (subclassing `Graph`, a much larger surface) rather than adding one independent hook that reads a value already available on every event it receives.

### 2. `run_id == session_id`; `build_graph()` (with the session manager wired) runs before the HTTP response, not inside the background task
`POST /debate/start`'s handler generates `run_id`, calls `build_graph()` with `FileSessionManager(session_id=run_id, storage_dir=SESSION_STORAGE_DIRECTORY)` wired via `set_session_manager`, and only *then* returns the response — by which point `Graph.__init__`'s synchronous `MultiAgentInitializedEvent` has already caused an initial checkpoint to be written to disk. The background `asyncio.Task` that actually drives `stream_async` is created after that, using the already-constructed graph.

Alternative considered: build the graph inside the background task, after the response has already been sent. Rejected: it reopens exactly the race this decision exists to close — if the process dies between "response sent" and "background task's first line runs," the client is holding a `run_id` with nothing on disk to resume from, violating the "resumable as soon as issued" requirement (specs/debate-durability/spec.md).

### 3. `GET /debate/resume/{run_id}`, not a new verb or a repurposed `/start`
Naming matches the pre-migration system's own endpoint for this (TRD Task 5's parity goal). It: rebuilds the graph against the existing session directory (same `run_id` as `session_id`), reads back `invocation_state.json` (Decision 1), creates a fresh `RunEntry` in the (now-empty, since it never survived the restart) `RunRegistry`, and re-drives the same background-task driver `POST /debate/start` uses — calling `graph.invoke_async`/`stream_async` again with the restored `invocation_state`. Strands' own `_resume_from_session` flag (set inside `deserialize_state()`) makes that call continue from `next_nodes_to_execute` rather than restart; if the run was paused on the audience-question interrupt, it re-pauses through the exact same `AudienceQuestionHook` path that runs on every other visit to that node — no branch in this change's own code needs to know or care whether the resumed run happens to be paused.

**Addendum (discovered during implementation):** `Graph.deserialize_state()` resets to a brand-new `GraphState` (status back to `PENDING`) whenever the persisted `next_nodes_to_execute` is empty. For *this* graph, that is not only true for a run that never started or one that already completed — `next_nodes_to_execute` also reads empty at *every round boundary*, because this graph's cyclic routing is driven entirely by `invocation_state["round"]`, not by Strands' own per-node bookkeeping, and its resume-readiness computation (`_compute_ready_nodes_for_resume`) can never mark an already-visited node — the revisited `moderator` hub — ready again. Confirmed directly against installed `strands` 1.53.0 by killing a run immediately after a round completes and resuming it: Strands' reset-and-reenter-from-the-entry-point response is still correct here, because `moderator` *is* the entry point and `round` alone decides where it routes next, so "reset and start over from the entry point" and "revisit the hub as the next round" turn out to be the same action for this graph shape. This means **`resume()` cannot use "does `next_nodes_to_execute` look empty" to decide whether a run is genuinely finished** — that signal is indistinguishable between "done" and "merely at a round boundary." `resume()` instead branches on the persisted `status` field directly: `"completed"`/`"failed"` are terminal (Strands only ever sets them once `_execute_graph` is fully exhausted or a node genuinely fails), `"interrupted"` means paused, and anything else (`"executing"`, `"pending"`, or no checkpoint written yet) is resumable and safe to drive via `stream_async` again, regardless of whether that particular resume happens to land on a round boundary or mid-round. `read_persisted_graph_status()` in `src/core/session.py` reads `status`/the pending interrupt id from the raw checkpoint file directly, *before* rebuilding the graph — never by rebuilding first and inspecting `graph.state.status` afterward, since deserialization on a genuinely-completed run resets `status` back to `PENDING` before the application ever gets to look at it.

Alternative considered: fold resume into `POST /debate/start` itself (e.g., "start" becomes "start-or-resume" if the `run_id` already has session state on disk). Rejected: `POST /debate/start` doesn't take a `run_id` as input today (it generates one) — overloading it to sometimes accept and resume an existing identifier changes an already-specified endpoint's contract for a case (restart recovery) that is conceptually a distinct operation, and the old system already modeled this as its own endpoint.

### 4. `SESSION_STORAGE_DIRECTORY` config, parallel to `MEMORY_PERSIST_DIRECTORY`
A new config value in `src/core/config.py`, project-local default, passed straight through as `FileSessionManager`'s `storage_dir`. No new config abstraction — this project already has exactly one pattern for "a local directory a component persists into" (`MEMORY_PERSIST_DIRECTORY` for the Chroma store), and this is the same shape of value.

### 5. Two-tiered test strategy: in-process simulated restart, plus exactly one real subprocess kill
Most coverage comes from tests that call `build_graph()` twice against the same `storage_dir`/`run_id` within a single test process (no real process kill) — cheap, deterministic, and able to target specific kill points (mid-round, mid-interrupt, immediately-after-start) directly, the same way `scaffolding-spike` and `audience-question-hitl` validated their own single-process assumptions without a real subprocess. Exactly one test spawns `server.py` as a real subprocess, sends it `SIGKILL` at a controlled point, restarts it, and drives the resume endpoint over HTTP — this is the literal exit criterion TRD Task 6 names ("kill process mid-debate, restart") and the in-process tests cannot claim to substitute for it, since they never exercise an `asyncio.Task` actually dying uncleanly or a fresh OS process starting cold.

Alternative considered: rely only on the in-process simulated-restart tests, treating the literal subprocess-kill test as redundant once the mechanism is proven. Rejected: the in-process tests construct a second `Graph` object in the same process that never actually stopped running — they prove the checkpoint/restore *mechanism* works, not that a real kill-and-restart does. TRD Task 6's own named test is specific enough (kill the process) that satisfying it needs at least one test that does exactly that.

## Risks / Trade-offs

- **[Risk]** Two independent files (`FileSessionManager`'s own checkpoint and this change's `invocation_state.json`) must stay consistent with each other — a crash between writing one and the other could leave them referring to different points in execution. → **Mitigation**: both writes are triggered from the same underlying events (`AfterNodeCallEvent`/`AfterMultiAgentInvocationEvent`), one node-completion apart from each other at most; on resume, `next_nodes_to_execute` names which node(s) are about to run next regardless of which of the two files is one write behind, and the worst case is a resumed node re-reading `invocation_state` that is missing only its own most recent field — which that same node is about to (re)write anyway.
- **[Risk]** `invocation_state.json` growing without bound for runs that are started but never resumed or explicitly cleaned up. → **Mitigation**: explicitly accepted for this change, matching `debate-fastapi-surface`'s own accepted risk for its in-memory `RunRegistry` (no eviction policy) — a retention/cleanup policy is deferred until real usage patterns are known.
- **[Trade-off]** This change's `invocation_state` persistence is entirely bespoke application code, not a Strands-native mechanism — it doesn't inherit the local→S3/AgentCore upgrade path the PRD documents for `FileSessionManager` itself. → **Accepted**: the PRD's own local-target scope (G4) only commits to `FileSessionManager` for the local phase; whatever the AWS-stage session backend turns out to be, this side-channel is a small enough, isolated enough piece of code to re-point at that point, and inventing a Strands-native equivalent that doesn't exist today is out of scope for this change.

## Migration Plan

No data migration — no debate run persisted anything before this change, so there is no existing on-disk format to carry forward or reconcile. Rollback is deleting the new files (the `HookProvider`, the config addition, the `GET /debate/resume/{run_id}` route) and no longer wiring a session manager into `build_graph()`; nothing outside this change's own files depends on any of it existing.
